# 视觉链路

## 约束

- 只有 `xgo26-camera.service` 可以创建 `Picamera2`，其他模块不得直接打开摄像头。
- 相机固定使用 OV5647 的 `1296x972`、4:3、10-bit 传感器模式，目标帧率 30 FPS。
- 服务持续生成同视场的 `main` 和 `lores` 两路 BGR 图像，并为每帧附加序号和传感器时间戳。
- 算法总是读取最新帧；处理落后时丢弃旧帧，不形成延迟队列。
- ROI 和目标位置优先使用归一化坐标，避免绑定某个输出分辨率。

## 消费者

| 消费者 | 数据流 | 默认尺寸 | 用途 |
| --- | --- | --- | --- |
| 浏览器 | `lores` MJPEG | 640x480 | 远程观察与现场调试 |
| 包裹/字母 YOLO | `main` raw 后缩放 | 模型输入尺寸 | 识别区语义检测、地面字母辅助确认 |
| 地面循迹 | `lores` raw | 320x240 | 黑线质心与方向修正 |
| 小球识别 | `lores` raw | 320x240 | 颜色分割与抓取对准 |
| 放置区几何 | `lores` raw | 640x480 | 圆形阵列、地面单应性与投放对准 |

服务原始帧为 BGR888，Python 客户端不需要 JPEG 解码。浏览器预览单独使用 JPEG，不进入正式算法链路。

## 硬件边界与总体策略

当前板端是 4 核 Cortex-A76、4GiB 内存的 Raspberry Pi CM5 Lite，没有独立 NPU；相机是 OV5647。实机上未经专门加速的 YOLO26n 已达到十几 FPS。当前 `xgovenv` 的 Torch/Torchvision 版本不匹配，因此部署端先使用训练模型导出的 ONNX 和 ONNX Runtime CPU 推理，不为追求峰值帧率提前引入 NCNN。

比赛任务不是五套视觉同时运行。状态机在任一时刻只启用一个主动算法：

```text
共享相机服务
    |
    +-- 浏览器预览：被动、低优先级，仅调试时打开
    +-- 循迹：传统视觉，持续闭环
    +-- 识别区：停车后运行 YOLO，多帧投票
    +-- 抓取区：已知目标颜色后的 LAB 分割，步进闭环
    +-- 放置区：场地几何 + 地面字母 + 单应性，步进闭环
```

这样可以避免模型推理影响循迹控制周期，也不需要常驻加载多个模型。浏览器客户端不得成为任务依赖；正赛无人查看时不产生 JPEG 编码开销。

## 场景设计

| 场景 | 姿态 | 输入 | 主算法 | 目标处理频率 | 结果 |
| --- | --- | --- | --- | --- | --- |
| 循迹 | `view_down` | `lores` 320x240 | 灰度阈值、扫描带、时序跟踪 | 20–30 Hz | 横向误差、方向误差、直角、置信度 |
| 识别区粗定位 | 中立观察姿态 | `lores` 640x480 | 箱体/矩形轮廓；必要时雷达测距 | 5–15 Hz | 箱体中心、偏航误差、接近状态 |
| 字母和图案 | 中立观察姿态，停车 | `main` 缩放至模型输入 | 单个 YOLO26n 模型 | 5–15 Hz | A–D、六类包裹、检测框、置信度 |
| 抓取区小球 | `grasp_view`，停车或短步进 | `lores` 320x240，必要时 640x480 | LAB 颜色分割、圆形/面积约束 | 10–20 Hz | 目标球中心、半径、颜色、置信度 |
| 放置区搜索 | 中立或轻微低头 | `main`/`lores` 640x480 | 外框、圆形阵列、字母候选 | 5–15 Hz | 放置区是否可见、排列方向、粗偏差 |
| 放置区精对准 | 固定 `place_view` | `lores` 640x480 | 去畸变、在线单应性、局部视觉伺服 | 10–20 Hz | 目标圆地面坐标、投放误差、重投影误差 |

表中频率是控制目标，不要求每次相机帧都处理。所有消费者读取最新帧，若算法尚未处理完则跳过中间帧。

### 循迹

沿用当前三扫描带算法，不运行 YOLO。近端点控制横向偏差，远近点连线估计方向，连续多帧确认直角。控制输出必须携带帧序号和置信度：帧过旧或连续丢线时停车，不能继续沿上一次命令盲走。

直线和轻微航向修正使用低头纯轮模式；直角处停车、确认角点方向、恢复中立姿态后使用正常转向，再重新进入低头循迹。这样视觉只承受轮式行进的小幅振动。

### 识别区箱体、字母和图案

两个箱体位于各自识别区中心且位置相对固定，其米制先验保存在 `maps/field_map.json`。导航先按循迹拓扑到观察位置，再利用箱体正面矩形或箱体边缘做局部居中和距离控制，完全停车后才进行语义识别。第一版不因此引入全场 SLAM；需要全局位姿时，可将雷达观测到的箱体平面与这两个已知中心进行匹配。

识别模型使用一套类别：

```text
A B C D clothes paper toothbrush apple orange banana
```

字母训练集同时包含箱体正面和地面俯视两种域，状态机负责解释当前检测含义，不额外拆出第二套常驻模型。`main` 流保留细节后裁剪箱体 ROI，再按模型输入尺寸 letterbox；不要直接把 1296x972 原图送入网络。

单帧结果不能直接生成配送任务。连续采集 7–11 个新帧，分别累计字母与图案置信度；要求二者在箱体正面 ROI 内、空间关系合理，并由多数投票得到唯一组合。低置信度时调整一次观察姿态或距离后重试，不能把上一个识别区的结果带入当前任务。

YOLO26n 当前速度已经足够。后续只有在模型推理明显阻塞控制或内存不足时，才评估 ONNX、NCNN 等后端；优化优先顺序是缩小输入、裁剪箱体 ROI、降低推理频率，然后才是更换推理后端。

### 抓取区小球

识别区已经确定目标颜色，抓取阶段只寻找一种颜色，不需要用 YOLO 重新分类。现有 LAB 阈值分割继续作为主方法，并增加：

- 最小/最大面积、圆度和半径范围，排除场地印刷色块。
- 连续帧位置与尺度一致性，避免把瞬时反光当作球。
- 搜索、横向修正、前后修正和可抓取四个阶段；每次短动作后停车取新帧。
- 用球中心和半径共同判断距离，最终抓取条件使用实测得到的图像窗口。

场上有两个同色球时，按“距离抓取窗口最近、轨迹连续”的候选优先；抓起后通过目标消失、夹爪状态和短暂停留共同确认，不仅依赖一次颜色检测。

### 放置区地面图案

放置区不能增加标记，但场地原有的 50x70cm 区域边界、四个圆形区域和 A/B/C/D 印刷内容就是允许使用的视觉锚点。这里采用两阶段方法：

1. 远处搜索阶段检测整排圆形和外框，确定放置区方向及目标大致方位。字母 YOLO 只用于确认 A–D 排列和处理局部遮挡。
2. 近处对准阶段检测原始几何，结合相机标定在线计算地面单应矩阵，把目标圆心转换为机器人局部坐标。

固定单应矩阵只能作为初值。机器狗负载、腿部姿态和地面起伏都会改变相机外参，因此每次能看到足够边界或圆心时都重新估计单应矩阵，并记录重投影误差。只有部分图案可见时使用上一帧矩阵短时跟踪；连续丢失后必须停车退回搜索状态。

正式控制不必每帧生成完整鸟瞰图，只转换外框角点、圆心和目标投放点；`warpPerspective` 生成的 BEV 图仅用于浏览器调试和日志。最终闭环控制的目标不是机器人中心，而是夹爪松开后的小球落点。需要实测标定“正确投放时目标圆在相机/BEV 中的位置”，将相机、机身和机械臂偏置一起吸收到投放窗口中。

放置过程按以下条件执行：

```text
发现放置区 -> 确认 A-D 顺序 -> 选择目标圆
-> 粗对准 -> 小步调整并重新观测
-> 目标进入投放窗口且连续多帧稳定
-> 松爪 -> 检查小球是否位于目标区域
```

视觉置信度不足、重投影误差超限或帧过旧时禁止松爪。当前 `drop_A/B/C/D` 的定时路线以后只负责到达搜索区域，不能直接触发 `_place_sequence()`。

任务状态机相应拆分为：

```text
GO_TO_DROP_SEARCH
SEARCH_DROP_ZONE
ALIGN_DROP_TARGET
CONFIRM_RELEASE_WINDOW
RELEASE_BALL
VERIFY_PLACEMENT
```

其中只有 `RELEASE_BALL` 可以调用夹爪松开动作；任何前置状态超时都保持持球并停车。

## 相机标定与姿态

像素位置不能直接换算厘米，也不要依赖尚未确认的标称 FOV。需要保存三类标定数据：

- 相机内参和畸变系数：使用棋盘格对 OV5647 标定，绑定 `1296x972` 传感器模式；其他 4:3 输出按比例缩放内参。
- 姿态外参初值：至少分别记录 `view_down`、`grasp_view`、`place_view` 的机身高度和俯仰角。
- 任务经验窗口：抓取时球的目标位置/半径，以及投放正确时目标圆相对夹爪落点的位置。

建议新增 `calibration/camera.json`、`calibration/postures.json` 和 `calibration/task_windows.json`，但在取得真实相机标定图和场地测量值前不创建虚假参数。相机安装、分辨率或机身姿态发生变化后必须重新验证。

曝光和白平衡先在场馆光照下自动稳定，再尽量锁定，避免 LAB 阈值随帧漂移。模型训练和调试数据必须覆盖开灯/关灯、阴影、不同接近距离、机身俯仰及机械臂遮挡。

## 统一输出约定

每个视觉结果至少包含：

```text
frame_sequence       相机帧序号
sensor_timestamp_ns  传感器时间戳
confidence           0.0–1.0
valid                是否满足当前任务使用条件
reason               无效或降级原因
```

各模块再附加自己的字段：

- 循迹：`lateral_error`、`heading_error`、`corner_direction`。
- 识别：`letter`、`package`、检测框和投票统计。
- 小球：`color`、中心、半径、轨迹稳定度。
- 放置：目标字母、目标圆心、局部前后/左右误差、偏航误差、重投影误差和可见锚点数。

任务状态机只消费 `valid=true` 且未过期的结果。调试图、掩码和 BEV 图属于旁路输出，不参与控制判断。

运行时记录每个算法的处理耗时、输入帧年龄、丢帧数和状态切换，不持续录制全部原始视频。默认只保存状态入口帧、最终采用帧、低置信度帧和失败前后的少量图像，既方便复盘，也减少 SD 卡写入和无效数据。

## 雷达辅助边界

如果第一轮实测发现识别区停车距离仅靠单目视觉不稳定，可以加入 YDLIDAR T-mini Plus。规则中唯一具有固定几何先验的立体地标是两个 `30x30x30cm` KT 板识别箱；外围围挡位置未确定，不能作为定位基准。点云应按连续性提取宽度接近 30cm 的有限平面段，拒绝长围挡和短小杂物，再估计箱体正面距离、中心和偏航。视觉继续负责确认识别箱体以及字母、图案语义；没有视觉箱体确认时，雷达估计不得触发运动。

雷达安装高度必须保证扫描平面低于 30cm 箱顶并能打到箱体，安装方向和相对机身外参也需要现场标定。两个箱体的身份由循迹状态和视觉共同确定，不能仅靠单帧点云区分识别区 1/2。雷达不适合识别地面 A-D，也不能替代放置区视觉对准。

当前尾部上方安装的静态初测得到：雷达原始 `+90°` 约对应机身正前方，雷达安装点约在机身中心后方 `0.29m`，配置中因此使用 `angle_offset_deg=-90` 和 `sensor_forward_offset_m=-0.29`。两个不同位置都在机器人坐标约 `-105°~-75°`、`0.08~0.10m` 处出现固定近距回波，已作为保守的自反射扇区，仅剔除 `0.13m` 内的点。前方黑色织物会因低反射产生缺点，不能把“无回波”直接判断为机械臂遮挡；`blind_sectors` 在宽白板对照实验完成前保持为空。

这一级融合不要求先搭建 ROS 或 SLAM。任务状态机只需要一个局部 `range/yaw/confidence` 接口，底层可以先直接使用 YDLidar SDK；确实需要点云工具链或全场定位时再迁移到 ROS 2。

## 实施顺序

1. 采集并固定 OV5647 内参，验证共享相机帧序号、延迟和曝光。
2. 完成循迹与直角实测，保证进入两个识别区的观察位置可重复。
3. 接入识别区 YOLO26n 后处理和多帧投票，先只输出结果不联动运动。
4. 完成目标颜色小球检测、分步对准和抓取确认。
5. 采集放置区远近视角，完成几何检测、地面单应性和投放窗口标定。
6. 最后评估识别区是否需要雷达，不因可能使用雷达提前引入全套 SLAM。

## 循迹视觉

`xgo26/line_following.py` 在画面下半部设置三条横向扫描带，从近到远寻找连续黑色区段。候选区段同时受宽度、上一层位置和前一帧位置约束，因此不会仅凭“最大黑色轮廓”选中地板接缝、墙面或圆形地标。

输出包含近端横向误差、远近点形成的方向误差、融合转向误差和置信度。运动层只使用融合误差，并在转向量增大时降低前进速度；连续丢线时按路线配置停车。`tools/test_line_vision.py` 只读取图像并输出标注图，不会初始化机器狗。

直角检测通过提取与纵向循迹带相接的横向黑带判断 `left/right`。检测到角点后，角点上方的扫描结果不会继续参与当前直线方向计算，避免把路锥、识别区边框等远处黑色目标当作循迹线。路线步骤可以设置 `stop_on_corner: right` 或 `left`，并用 `corner_frames` 要求连续多帧确认；当前正式路线尚未启用该条件。

四轮低头姿态 `view_down` 保持正常高度 `translation('z', 95)`，默认使用 `attitude('p', 20)`。板端 XGOMINI 版 `xgolib` 的实际俯仰限幅为 `±22°`，比赛动作层按该值保护。三段循迹默认持续使用低头姿态和四轮差速修正；切换到正常步态转向前会自动恢复中立俯仰角，再进入轮行时重新应用所选姿态。箱体识别等后续纵向移动默认使用中立四轮姿态。

## HTTP 接口

```text
GET /health
GET /stream.mjpg?stream=lores
GET /snapshot.jpg?stream=main
GET /frame.raw?stream=lores&after=<sequence>
```

`frame.raw` 响应头包含宽、高、通道数、帧序号和 `SensorTimestamp`。正常任务代码通过 `CameraServiceClient` 使用该接口，不直接解析响应头。

响应同时携带当前帧的 `ExposureTime` 和 `AnalogueGain`，图片采集器将其连同亮度、截断比例和清晰度写入 `frames.jsonl`。`config.json` 的 `camera.controls` 支持自动曝光/白平衡以及固定曝光、增益和色彩增益；默认保持自动控制，只有完成现场测光和运动模糊测试后才固定参数。

YOLO 数据使用 `tools/capture_yolo_images.py` 从共享 `main` 码流采集。采集器保存完整原图而不是 ROI 裁图，确保以后可以调整框选规范、ROI 和模型输入尺寸。自动采集与浏览器预览、传统视觉和键盘遥控可以并行运行，不会创建第二个 Picamera2 实例。

## 服务切换

仓库提供 `deploy/systemd/xgo26-camera.service`。它与厂商 `oumax-camera.service` 都使用摄像头和 8090 端口，不能同时运行。

切换到比赛服务：

```bash
sudo systemctl disable --now oumax-camera.service
sudo install -m 644 deploy/systemd/xgo26-camera.service /etc/systemd/system/xgo26-camera.service
sudo systemctl daemon-reload
sudo systemctl enable --now xgo26-camera.service
```

恢复厂商服务：

```bash
sudo systemctl disable --now xgo26-camera.service
sudo systemctl enable --now oumax-camera.service
```

不要直接修改 `/home/pi/oumax-xgo/picam_mjpeg_server.py`，以便随时回退厂商环境。
